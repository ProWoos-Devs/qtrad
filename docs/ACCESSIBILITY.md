# Accessibility in 1.8.0

Editor language controls are native toggle buttons in a named group. Full native language names remain visible; `aria-pressed` describes the current language. Tab moves between buttons, Enter/Space activates them, and focus stays on the selected button. A polite status region announces the chosen language. Buttons remain disabled until the script initializes; raw mode has explanatory text instead of misleading controls.

Editor fields receive language/locale and direction attributes, including the WordPress block editor's iframe canvas and TinyMCE content. Native names use bidirectional isolation. Plugin buttons/public switcher links have minimum 44-pixel targets, wrapping layouts and visible focus. Selection is also indicated by underlining. Logical CSS margins support RTL. Forced-colors mode exposes flag names and keeps focus/selection visible; flags are decorative images with empty alt text.

Public switchers are labelled navigation with ordinary links and `aria-current` on the current language. Short-code and flag styles still expose full names to assistive technology. A missing flag shows the language name. The dropdown has a visible label and explicit Go button: selecting an option does not navigate. Without JavaScript, ordinary language links remain usable. This follows [WCAG's guidance on changes of context on input](https://www.w3.org/WAI/WCAG22/Understanding/on-input.html) and the [ARIA button pattern](https://www.w3.org/WAI/ARIA/apg/patterns/button/).

Settings and term fields use native labels and fieldset legends. Invalid language/domain entries produce an error notice, focus it after navigation and retain the invalid editable values. Settings confirmation and editing-language announcements use status semantics. The plugin's interface strings use the `qtrad` text domain; a translation template is included, but translated interface catalogues have not yet been supplied.

SEO translation fields use native labels and per-language fieldset legends, carry language/direction attributes, and work without JavaScript. Classic and block editor metabox saves retain other/disabled translations. Bundled SVG flags remain decorative; saved empty/missing flag choices retain readable names.

## Verification

The original recorded browser run uses Chromium against WordPress 6.8. The completed 1.8.0 matrix also runs Chromium against WordPress 5.8/PHP 7.4 and WordPress 7.1.2/PHP 8.5. Both pass 42 browser assertions with no JavaScript errors or axe violations; their executed reports are in ../tests/results/matrix/. Checks cover keyboard switching/focus, live announcements, repeated classic/block saves, SEO-panel saves, clean save state, Arabic direction/language, narrow 320-CSS-pixel public layouts, forced colors, explicit dropdown navigation and no-JavaScript links. Axe-core 4.10.3 checks WCAG A/AA rule tags through WCAG 2.2 on plugin switchers, language controls, SEO fields, settings and taxonomy fields. The older results remain in `../tests/results/browser-wordpress-6.8.json`.

Automated checks are scoped to plugin controls. They are not a WCAG conformance certification for the whole WordPress editor, a theme or the site. Axe leaves color-contrast items for manual review in some tested scopes; each report records these incomplete checks. Closed disclosure contents should also be checked when expanded. Manual testing with NVDA/Firefox, VoiceOver/Safari, speech input, keyboard-only workflows, 200–400% zoom and user themes remains necessary before claiming full accessibility support. Dynamic announcements should be checked for clarity with actual screen readers, not just DOM attributes.
